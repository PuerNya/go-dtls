# Contributing

[简体中文](CONTRIBUTING.md) | [English](CONTRIBUTING.en.md) | [Русский](CONTRIBUTING.ru.md)

Спасибо за участие в разработке `go-dtls`. Изменения должны сохранять семантику дейтаграмм DTLS 1.3, безопасность протокола и существующую производительность. Не создавайте заранее инфраструктуру для расширений без конкретной потребности.

## Среда разработки

- Go 1.26 или новее.
- golangci-lint v2.12.2 — та же версия, что и в CI.
- Для race-тестов Windows нужны Zig 0.17 и рабочая цепочка CGO.
- Если изменение затрагивает возможность, поддерживаемую wolfSSL, тесты совместимости и специализированные benchmark с wolfSSL обязательны; для остальных изменений wolfSSL не требуется.

## Обязательные проверки

Все исходные файлы Go должны соответствовать конфигурации formatter в golangci-lint v2.12.2. Каждый commit и pull request обязан пройти format, module, lint, test, shuffle, checkptr, vet и race. В Linux, macOS и CI выполняйте:

```sh
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.12.2 fmt --diff
go mod verify
go mod tidy -diff
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.12.2 run ./...
go test ./... -count=1
go test ./... -shuffle=on -count=1
go test ./... -gcflags=all=-d=checkptr=2 -count=1
go vet ./...
go test -race ./... -count=1
```

Для изменений протокола, конкурентного кода или жизненного цикла ресурсов также запускайте повторные тесты:

```sh
go test ./... -count=10 -timeout=10m
```

В Windows выполните все команды выше, кроме последней команды race, и замените ее скриптом репозитория:

```powershell
.\tools\test-race.ps1
```

GitHub Actions независимо выполняет восемь обязательных job для каждого push и pull request; job module последовательно запускает verify и tidy diff. Любую ошибку необходимо исправить; нельзя обходить ее ослаблением проверок, пропуском тестов или расширением исключений lint.

## Изменения протокола

Поведение протокола следует RFC 9147, RFC 9846 и применимым связанным RFC:

- `MUST`, `MUST NOT`, `REQUIRED`, `SHALL` и `SHALL NOT` должны строго применяться клиентом и сервером при отправке и приеме.
- Клиент активно реализует требования класса `SHOULD`. Сервер может допускать отклонения узла только без ослабления аутентификации, конфиденциальности, защиты от повторов, ограничений усиления и согласованности состояния.
- После согласования возможности `MAY` или `OPTIONAL` все ее условные обязательные требования должны быть полностью реализованы.
- Сохраняйте соответствие одного `WriteDatagram` одной записи Application Data. Не добавляйте неявную фрагментацию, упорядочивание или повторную передачу прикладных данных.
- Используйте существующие record, flight, ACK, transcript, key schedule, CID и типы ошибок, а не дублируйте их state machine.

Изменения протокола должны как минимум покрывать:

- Нормальный путь, а также malformed, truncated, duplicate, unknown и выходящие за границы входные данные.
- Все затронутые ветви клиента и сервера, отправки и приема, полного рукопожатия и возобновления.
- Потери, задержку, изменение порядка и дублирование; изменения повторной передачи или state machine требуют многократной проверки.
- Связанные границы безопасности: anti-replay, ограничения усиления и использования AEAD, очистку секретов и ограничения ресурсов.
- Жизненный цикл тайм-аутов, закрытия, goroutine, памяти и сессий Listener.

Для изменений повторной передачи, рукопожатия или state machine протокола запускайте соответствующие тесты слабой сети и end-to-end с `-count=100`. Тесты жизненного цикла ресурсов запускайте как минимум с `-count=10`.

Необязательные расширения требуют конкретной потребности развертывания и проверяемого дизайна протокола. Не добавляйте заранее API-заглушки или пустую инфраструктуру.

## Проверка производительности

Изменения горячих путей рукопожатия, record, parsing, allocation или конкурентного кода должны проверяться и микротестами, и полными соединениями. Полное соединение — основной критерий производительности; локальный микротест не доказывает общую производительность.

```sh
go test -run '^$' -bench . -benchmem
go test -run '^$' -bench '^BenchmarkConnectionHandshakeLifecycle$' -benchmem -benchtime=2000x -cpu=1
go test -run '^$' -bench '^BenchmarkMutualTLSHandshakeLifecycle/(Full|Resumed)$' -benchmem -count=10
go test -run '^$' -bench '^BenchmarkCertificateCompression' -benchmem
go test -run '^$' -bench '^BenchmarkProtectedRecord(Seal|RoundTripInPlace)$' -benchmem -count=5
```

При сравнении производительности до и после изменения:

- Фиксируйте версию Go, CPU, `-cpu` и `-benchtime`.
- Заранее компилируйте тестовые бинарные файлы до и после изменения. Для полных соединений используйте `-cpu=1`, 500 итераций на выборку, чередуйте бинарные файлы не менее девяти циклов и сравнивайте парные медианы.
- Совместно проверяйте `ns/op`, `B/op`, `allocs/op`, пропускную способность полного соединения и жизненный цикл ресурсов.
- При различиях в allocation или памяти используйте профили, чтобы определить точный объект и путь вызовов.
- Храните результаты benchmark, профили и временные бинарные файлы вне репозитория. Не добавляйте созданные артефакты в commit.

Workflow benchmark для pull request автоматически выполняет это парное сравнение base/head. Проверка завершается ошибкой, если парная медиана времени выросла более чем на 5% и большинство пар медленнее, либо если медиана `B/op` или `allocs/op` выросла как минимум в 75% пар. Изменение исходного кода workload benchmark по умолчанию считается несопоставимым и приводит к ошибке; после проверки сопровождающий может добавить метку `performance-workload-approved`, но отчет не вычисляет разницу между разными workload. Отсутствующие benchmark, метрики или парные замеры также приводят к ошибке; решение и исходный вывод сохраняются в комментарии PR и artifact.

README содержит только репрезентативную производительность текущей среды. A/B, замороженная база и описание различий до/после относятся к подтверждениям в pull request.

## Проверка совместимости

Если другая реализация поддерживает возможность, добавляйте двунаправленные сторонние end-to-end тесты. Тесты wolfSSL запускаются так:

```powershell
$env:WOLFSSL_ROOT = 'C:\path\to\wolfssl'
go test -run TestInteropWolfSSL -v -count=10
```

Если wolfSSL поддерживает целевую возможность, также обязательно добавьте и запустите специализированный benchmark через настоящий UDP для go-dtls -> go-dtls, go-dtls -> wolfSSL, wolfSSL -> go-dtls и wolfSSL -> wolfSSL. Включите commit и конфигурацию сборки другой реализации, workload, границы измерения, медиану пяти запусков и ограничения в подтверждения pull request; не помещайте данные межреализационных benchmark в README.

Формальный четырехсторонний benchmark использует `go test -json`. Каждое применимое направление workload должно дать пять результатов либо совпасть с точной причиной skip и подтверждением, зарегистрированными для полного SHA wolfSSL. Новый SHA, восстановленная возможность, измененная причина, неизвестный skip, отсутствующее направление или недостаточное число замеров приводят к ошибке генерации отчета и workflow. Разрешенные ограничения другой реализации должны быть видны в отчете.

Workflow benchmark использует точный SHA wolfSSL, определенный для данного запуска, и выполняет полную матрицу совместимости до тестов производительности: один проход для pull request и десять для push в `master`, плановых и ручных запусков. Любая неожиданная ошибка блокирует отчет и публикацию. Cache сборки wolfSSL сохраняется до запуска матрицы, поэтому ошибка теста не требует повторной компиляции при следующем запуске.

После push в `master` workflow benchmark обновляет отдельную ветку `benchmark-results`. Плановая проверка запускает тесты и публикует результат, только если изменился SHA ветки `master` go-dtls или wolfSSL и для этого SHA go-dtls нет benchmark в очереди или в процессе выполнения. Pull request обновляет только комментарий с результатами на своей странице и никогда не записывает данные в `master` или ветку результатов. Не поддерживайте показатели производительности в README вручную.

Каждый checkout, выполняющий код pull request, должен задавать `persist-credentials: false` и до запуска кода репозитория проверять, что локальная конфигурация Git и URL origin не содержат token workflow. Job benchmark для PR имеет только права чтения; право записи в PR есть лишь у доверенного job комментария `workflow_run`. Недоверенный artifact benchmark должен быть единственным, иметь ограниченный размер, содержать только ожидаемые обычные файлы и повторно разбираться и экранироваться генератором отчета из ветки по умолчанию; любое нарушение этих границ должно завершать workflow ошибкой.

При добавлении или переименовании любого benchmark или sub-benchmark необходимо обновить его категорию, порядок и многоязычные подписи в `tools/benchmark-report`. Генератор отчета отклоняет вывод benchmark без явного покрытия, а workflow benchmark должен успешно пройти.

Если сторонняя реализация не включает или не поддерживает целевое расширение, явно укажите границу совместимости. Нельзя выдавать пропущенный тест за успешно пройденный.

## Документация

- Изменения публичного API, конфигурации, ошибок или поведения протокола должны обновлять Go doc и все языковые версии README.
- Синхронизируйте содержание на китайском, английском и русском языках и сохраняйте работоспособность всех ссылок переключения языка.
- README описывает только существующие возможности, полноту RFC, текущие ограничения, использование, репрезентативную производительность и покрытие тестами.
- Неподдерживаемые возможности перечисляются кратко. Планы, приоритеты, история исследований и исторические сравнения производительности не относятся к README.

## Commit и pull request

Тема каждого commit должна соответствовать Conventional Commits:

```text
type(scope): description
```

Примеры:

```text
feat(cid): implement RFC 9853 return routability checks
fix(record): reject invalid truncated sequence numbers
docs(api): clarify datagram truncation behavior
```

Заголовок pull request должен использовать тот же формат. Workflow Conventional Commits проверяет заголовок PR и тему каждого commit в ветке, а после изменения заголовка запускается повторно.

В pull request укажите применимые разделы RFC, изменения поведения, результаты тестов и race, данные производительности и границы совместимости. Для несовместимого изменения используйте `!` и объясните миграцию в тексте.
